# Myfirstpro Desktop — دليل المطوّر

برنامج سطح مكتب لـ **Windows فقط** (10 و11) يشغّل «النسخة الأولى التجريبية لبرنامج المحاسبات لمواد البناء» **بدون إنترنت بالكامل**، داخل Electron، مع تثبيت احترافي، كود تفعيل، تحديث داخلي موقّع، وحماية للملفات. الإصدار الحالي للمنصة 1.0.0 (البرنامج الداخلي: الويب 5.2 ولم يتغيّر).

> نظام macOS غير مفعّل الآن، لكن التصميم جاهز لإضافته بدون إعادة بناء (انظر «macOS لاحقًا»).

---

## 1) فكرة التفعيل في سطر واحد

**أنت ترسل للعميل كود واحد فقط. العميل يلصقه ويشتغل.** لا كود جهاز ولا ملفات ولا تبادل.

| نوع الكود | يعمل لمدة |
|---|---|
| دائم | بدون انتهاء |
| دقائق | N دقيقة تبدأ من **أول تفعيل** على جهاز العميل |
| ساعات | N ساعة من أول تفعيل |
| أيام | N يوم من أول تفعيل |

* المدة **لا تبدأ عند إصدار الكود** بل عند أول لصق له، وتُسجَّل على جهاز العميل.
* **بعد أي تحديث للبرنامج** (تغيّر رقم الإصدار) تظهر شاشة التفعيل ويُطلب الكود **مرة ثانية**. العميل يلصق **نفس الكود**، فيكمل من حيث توقف: المدة **لا تبدأ من جديد**. لذلك شاشة التفعيل وكل رسالة تخرج من المولّد فيها تنبيه «احتفظ بالكود».
* إذا انتهت المدة يُقفل البرنامج في لحظة الانتهاء تمامًا (وليس بعد ساعات)، **وبيانات العميل تبقى كما هي** ويقدر يصدّر نسخة منها من شاشة القفل.
* **مهلة التفعيل**: كل كود له مهلة يجب أن يُفعَّل خلالها (افتراضي 30 يومًا للمؤقت و365 للدائم، و`0` = بدون حد). تمنع استخدام كود قديم من زمان.

### كيف تُصدر الأكواد؟

**من داخل نسخة المطوّر (الأسهل):** شغّل نسخة Developer ← على شاشة التفعيل اضغط «مولّد أكواد التفعيل…» (أو من القائمة: المطوّر ← مولّد أكواد التفعيل). اكتب كلمة مرور المطوّر ← اختر النسخة (Production للعملاء) ← النوع والمدة (أو اضغط مدة جاهزة: ساعة / 24 ساعة / 7 أيام / 30 يومًا / سنة / دائم) ← اسم العميل (اختياري) ← «إصدار الكود». بعدها «نسخ الكود» أو **«نسخ رسالة جاهزة للعميل»** (فيها الكود والمدة وتنبيه الاحتفاظ بالكود) وتبعتها واتساب. كل كود يُحفظ في سجل محلي لتعيد إرساله لاحقًا.

**من سطر الأوامر:**
```
DEVPW='كلمة-المرور' node tools/make-license.js --channel production --hours 24 --label "اسم العميل" --message
DEVPW=… node tools/make-license.js --channel production --minutes 30
DEVPW=… node tools/make-license.js --channel production --days 7 --within-days 14
DEVPW=… node tools/make-license.js --channel production --permanent --count 5
```

**دخول المطوّر بدون كود:** في نسخة Developer على شاشة التفعيل اكتب كلمة مرور المطوّر واضغط «دخول بدون كود». (لا يُحفظ؛ يُطلب في كل مرة.)

## 2) المجلدات

```
desktop/
  config/channels.json     هوية كل نسخة (Production / Developer) وعنوان التحديث
  src/main/                البرنامج الرئيسي (main.js) + lib/ (تشفير، أكواد، حالة، بيانات، تحديث) + platform/ (win32 / darwin / linux)
  src/preload/             الجسر الصغير بين النوافذ والبرنامج
  src/renderer/            شاشة التفعيل + شاشة المولّد (للمطوّر فقط) + الخط
  tools/                   build / init-keys / make-license / make-update / verify-artifact / compose-renderer
  assets/                  الشعار والأيقونة وصور المثبّت (make-brand.py)
  test/unit, test/e2e      الاختبارات
  keys/  (غير مرفوع)       الخزائن المشفّرة للمفاتيح — لا تُنشر ولا تدخل Git
  dist/  build/ (غير مرفوع) ناتج البناء
```

## 3) التجهيز لأول مرة

```
npm install
DEVPW='كلمة-مرور-قوية-12-حرف-أو-أكثر' node tools/init-keys.js --channel production
DEVPW='نفس-الكلمة'                     node tools/init-keys.js --channel developer
```
* ينشئ لكل نسخة: مفتاح توقيع الأكواد + مفتاح توقيع التحديثات + مفتاح تشفير البرنامج. الخاص منها لا يُكتب إلا داخل `keys/<نسخة>/vault.json` **مشفّرًا بكلمة المرور** (scrypt + AES-256-GCM)، والعام فقط يدخل البرنامج.
* **احتفظ بنسخة احتياطية من مجلد `keys/` وكلمة المرور في مكان آمن.** لو ضاعت لن تستطيع إصدار أكواد أو تحديثات لنسخ موجودة عند العملاء. والأداة ترفض الكتابة فوق مفاتيح موجودة إلا بـ `--force`.
* كلمة المرور تُقرأ **فقط** من متغير البيئة `DEVPW` لحظة تشغيل الأمر، ولا تُحفظ ولا تُطبع.
* تغيير كلمة المرور لاحقًا **بدون** مفاتيح جديدة (لا يتأثر أي عميل): `OLDPW=… NEWPW=… node tools/change-password.js` ثم أعد بناء نسخة Developer (لأنها تحمل الخزائن). نسخ Production لا تحمل أي خزنة فلا تتأثر.

## 4) البناء (على Windows أو على Linux)

```
DEVPW=… node tools/build.js --channel developer  --version 1.0.0
DEVPW=… node tools/build.js --channel production --version 1.0.0
node tools/verify-artifact.js --channel production --dir dist/production      # فحص الناتج فعليًا
```
الناتج: `dist/<نسخة>/Myfirstpro-Desktop-Setup-1.0.0.exe` (والمطوّر `Myfirstpro-Desktop-Developer-Setup-1.0.0.exe`).

| | Production | Developer |
|---|---|---|
| الاسم والهوية | Myfirstpro Desktop | Myfirstpro Desktop (Developer) |
| appId / مجلد البيانات | منفصلان تمامًا | منفصلان تمامًا (يتجاور معه على نفس الجهاز) |
| مفاتيح الأكواد والتحديث | خاصة بها | خاصة بها (كود نسخة لا يعمل في الأخرى) |
| أدوات المطوّر (F12 / إعادة تحميل) | **معطّلة** | مفعّلة، وشريط أحمر وعنوان `[DEVELOPER]` |
| مولّد الأكواد + الخزائن المشفّرة | **غير موجودة في الملفات أصلًا** | موجودة (محمية بكلمة المرور) |
| مفاتيح الاختبار (ساعة وهمية…) | **تُتجاهل** | مفعّلة للاختبار الآلي فقط |

* تثبيت لكل مستخدم (بدون طلب صلاحيات مدير)، معالج Next / Next / Finish بالعربية، اختصار سطح المكتب وقائمة ابدأ، وإلغاء التثبيت **لا يحذف بيانات العميل**.
* المثبّت **غير موقّع رقميًا** (لا توجد شهادة Code Signing)، فيظهر تحذير Windows SmartScreen أول مرة («مزيد من المعلومات ← تشغيل على أي حال»). لإزالته اشترِ شهادة ووفّر `CSC_LINK` / `CSC_KEY_PASSWORD` وقت البناء. لا علاقة له بتفعيل الأكواد.

## 5) التحديثات

```
DEVPW=… node tools/make-update.js --channel production --installer dist/production/Myfirstpro-Desktop-Setup-1.0.1.exe --version 1.0.1 --notes "ما الجديد" [--min 1.0.0] [--revoke LIC-XXXXXXXXXX]
```
ينتج `update.json` (بيان موقّع للتحقق أونلاين) وملف `.mpupdate` (ملف واحد يعمل **بدون إنترنت**).

* **داخل البرنامج:** مساعدة ← «البحث عن تحديث…» (HTTPS فقط) أو «تحديث من ملف…» (`.mpupdate`). يمكن تفعيل «التحقق التلقائي عند التشغيل» (مغلق افتراضيًا؛ البرنامج لا يتصل بالإنترنت من نفسه أبدًا).
* **كل تحديث يُفحص قبل التثبيت:** توقيع ECDSA بمفتاح التحديث، النسخة والقناة والمنصة، حجم وبصمة SHA-512 للمثبّت، **ممنوع الرجوع لنسخة أقدم** وممنوع إعادة بيان أقدم (رقم تسلسلي)، ثم نسخة احتياطية لبيانات العميل، ثم تثبيت صامت وإعادة فتح البرنامج.
* **إيقاف كود:** `--revoke LIC-…` داخل بيان موقّع؛ يطبّقه البرنامج عند أول تحديث يقبله.
* بعد التحديث **يطلب البرنامج كود التفعيل مرة ثانية** (انظر أعلاه) والبيانات كما هي.
* مكان النشر المقترح: GitHub Pages (`/desktop/update.json` و`/desktop/dev/update.json`) والمثبّت ملف في Releases. **لا ترفع `keys/` أبدًا.**

## 6) بيانات العميل

* تُحفظ في `%APPDATA%\Myfirstpro Desktop\` (مرآة بيانات بإدارة البرنامج نفسه، تحقق ببصمة، نسخ احتياطية دوّارة، نسخة قبل كل تحديث)، فلا تضيع لو تغيّر متصفح أو مسح تخزينه.
* التصدير: ملف ← «تصدير نسخة من البيانات…» (وحتى من شاشة القفل بعد انتهاء الكود).

## 7) الحماية — ما تفعله وما لا تفعله (بصراحة)

**يفعل:**
* البرنامج الداخلي مشفّر (AES-256-GCM) داخل `app.enc`، ومفتاحه **لا يُخزَّن في أي ملف**: يصل مع كود التفعيل نفسه (ملفوفًا ومربوطًا بتوقيعه) ويُفك في الذاكرة فقط.
* لا يمكن تعديل كود (المدة/النوع/النسخة) دون إبطال توقيعه؛ كود نسخة لا يعمل في الأخرى.
* ملفات التطبيق داخل `app.asar` مع فحص سلامة، وإيقاف `RunAsNode` والفحص عن بعد وتحميل التطبيق من غير asar (Electron Fuses). النوافذ تحمل صفحات `mpd://app` فقط، CSP صارم، بلا Node في الصفحات، وشبكة الصفحات مقطوعة، وكل واجهة IPC تتحقق من المرسل.
* ساعة الجهاز: الرجوع بالتاريخ للخلف يُقفل الأكواد المؤقتة (حالة موقّعة بـ HMAC في 3 أماكن + أحدث تاريخ لملفات البيانات كشاهد).
* مسح الحالة المحفوظة لا يعيد المدة بعد انتهاء «مهلة التفعيل» للكود.

**لا يفعل (حدود حقيقية — هذه حماية «ترفع الصعوبة» وليست DRM):**
* الكود **ليس مربوطًا بجهاز واحد** (هذا هو المقابل لبساطة «كود واحد»): من يملك الكود يقدر يستخدمه على أكثر من جهاز، وكل جهاز يعدّ مدته من أول تفعيل عنده. للتحكم: اعطِ كل عميل كودًا بعميله (اسم في السجل) ومدة قصيرة، واستخدم الإيقاف عبر التحديث.
* مستخدم بصلاحيات مدير ومعرفة تقنية عالية يستطيع مسح حالة التفعيل المحلية فتبدأ مدة كود مؤقت من جديد **ما دام داخل مهلة التفعيل**؛ لذلك اجعل مهلة الأكواد المؤقتة قصيرة.
* من يملك نسخة Developer **وكلمة المرور** يقدر يصدر أي كود؛ ومن يسرق ملف نسخة Developer يحتاج كلمة المرور لفتح الخزائن (scrypt بتكلفة عالية) — فاستعمل كلمة مرور طويلة عشوائية ولا تعطِ نسخة Developer لأحد.
* لم نجرّب المثبّت والتطبيق على **Windows حقيقي** في بيئة البناء (استُخدم Wine للمثبّت وLinux لاختبار البرنامج). جرّب على جهاز Windows 10/11 قبل التسليم.

## 8) Windows 7

الاختبار التقني أثبت أن الحمولة (الصفحة المشفرة والمنطق) تعمل على Electron 22 (آخر إصدار يدعم Win7) لكن:
* Win7 لم يعد مدعومًا من Chromium/Electron الحديثين، فيلزم **قناة قديمة منفصلة** (Electron 22.x) بمثبّت وخيارات أمان أقل (لا تتوفر بعض الـ Fuses والتحديثات الأمنية).
* يُنصح بتأجيله حتى يطلبه عميل فعليًا، وبناؤه بقناة ثالثة `legacy` في `config/channels.json` دون المساس بالقناتين الحاليتين.

## 9) macOS لاحقًا (مصمَّم، غير مفعّل)

* كل ما يخص نظام التشغيل في `src/main/platform/` (`win32.js` فقط مدعوم، و`darwin.js` معرّف ويرفض العمل حاليًا): هوية الجهاز، تشغيل المثبّت، الامتداد.
* بيانات التحديث تحمل `plat` (حاليًا `win32`) و`arch`، وأسماء المجلدات تأتي من `app.getPath` لا من مسارات Windows.
* المتبقي عند الحاجة: تعبئة `darwin.js`، هدف `dmg/zip` في `build.js`، توقيع Apple وNotarization، وصيغة التحديث لـ `.dmg`/`.zip`. لا شيء في المنطق (الأكواد، الحالة، البيانات، التحديث) يحتاج إعادة كتابة.

## 10) الاختبارات

```
node --test test/unit/*.test.js                         # وحدات: أكواد، حالة، بيانات، تحديث، خزنة، مولّد
DEVPW=… KEYS=<مجلد-مفاتيح-اختبار> xvfb-run -a node test/e2e/e2e.mjs   # البرنامج الحقيقي تحت Electron (يتضمن اختبار كود دقيقة حقيقية ~70 ثانية)
node tools/verify-artifact.js --channel production --dir dist/production
```
اختبر دائمًا بمفاتيح تجريبية في مكان مؤقت — لا تستعمل خزائن الإنتاج في الاختبارات.
